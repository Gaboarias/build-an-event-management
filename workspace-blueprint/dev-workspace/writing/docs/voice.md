# Voice Guide

## The Core

Write like a skilled developer talking to another developer. Direct. Precise. No fluff.

---

## Tone

**Default tone:** Clear, confident, respectful of the reader's time.

- Say what you mean in the fewest words that are still accurate
- Prefer active voice: "The function returns X" not "X is returned by the function"
- Use second person ("you") when addressing the reader directly
- Don't be stiff. Contractions are fine. Personality is fine.

**Not this:**
> It is important to note that the authentication process requires the provision of valid credentials in order to proceed.

**This:**
> Authentication requires valid credentials. No credentials, no access.

---

## What We Don't Do

- **No hype words**: "powerful", "robust", "seamless", "game-changing", "cutting-edge"
- **No filler openers**: "In today's fast-paced world...", "Great question!", "Certainly!"
- **No passive hedging**: "It might be worth considering...", "This could potentially..."
- **No over-explanation**: If the reader can figure it out, don't explain it
- **No AI-isms**: Unnaturally smooth transitions, lists for everything, excessive summarizing

---

## Technical Content

- Lead with the problem, then the solution
- Code examples should be minimal — show the thing, not every edge case
- Name things clearly. Abbreviated variable names in examples make docs harder to read
- When something is opinionated, say so. "We chose X because Y" beats "X is the best approach"

---

## Specs and PRDs

- State the problem in one sentence before anything else
- Scope explicitly: what's in, what's out
- Acceptance criteria are pass/fail — not vague descriptors
- If it can't be tested, it's not a requirement — it's a wish

---

## READMEs

Structure:
1. What it is (1-2 sentences)
2. Install / quick start
3. Usage (most common case first)
4. Configuration / options (if needed)
5. Contributing / license (if applicable)

No wall of text before the install instructions.

---

## Blog Posts

- Hook in the first sentence — not a preamble
- One specific idea per post
- Show, don't just tell — code, examples, concrete outcomes
- End with a clear takeaway, not a summary of what you just said
